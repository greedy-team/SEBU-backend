# Flyway 변경 기준

- 작성일: 2026-08-17

## 버전 파일

- `src/main/resources/db/migration`에서 현재 최고 버전을 찾고 `V{다음 번호}__{영문 설명}.sql`을 추가한다.
- 영문 설명은 변경 목적이 드러나는 소문자 snake_case로 작성한다.
- 적용된 버전 파일은 체크섬이 바뀌지 않도록 수정, 이름 변경, 삭제하지 않는다.
- 오류를 바로잡을 때도 새 버전 파일에서 전진 수정한다.
- 로컬 전용 데이터는 운영 마이그레이션과 분리한다.

## 안전한 스키마 변경

- 새 구조 추가, 기존 데이터 보정, 제약 강화, 이전 구조 제거 순서로 나눈다.
- NOT NULL 컬럼은 기존 행을 채울 방법을 먼저 마련한 뒤 제약을 적용한다.
- 컬럼 이름 변경은 새 컬럼 추가, 데이터 복사, 애플리케이션 전환, 이전 컬럼 제거로 나누는 방식을 우선한다.
- 컬럼·테이블 삭제, 타입 범위 축소, 기존 값을 잃는 변환은 사용자 승인과 데이터 보존 계획이 있어야 한다.
- 대량 갱신과 인덱스·제약조건 추가는 실행 시간과 테이블 잠금 가능성을 검토한다.

## 제약조건과 인덱스

- 기존 명명 규칙에 맞춰 기본 키는 `pk_`, 외래 키는 `fk_`, 고유 제약은 `uk_`, CHECK 제약은 `ck_`, 인덱스는 `idx_`를 사용한다.
- 외래 키 타입을 참조 키와 일치시키고 `ON DELETE` 동작을 명시한다.
- 조회·조인·정렬 조건을 근거로 인덱스를 추가하며 기본 키나 고유 제약과 중복하지 않는다.
- CHECK 제약의 값은 Java enum 값과 일치시킨다.

## JPA 정합성

- `@Table`, `@Column`, `@JoinColumn`, `@UniqueConstraint`, `@Enumerated`와 SQL 정의를 비교한다.
- 문자열 길이, NULL 허용 여부, 선택적 연관관계, 시간 컬럼을 양쪽에서 일치시킨다.
- Hibernate의 스키마 검증은 정합성 확인에만 사용하고 스키마 자동 변경에 의존하지 않는다.

## 검증

- 빈 DB에서 첫 버전부터 새 버전까지 순서대로 적용한다.
- 기존 데이터가 있는 상태에서 데이터 보정과 제약 추가가 성공하는지 확인한다.
- H2의 MySQL 모드에서 통과해도 `ALTER TABLE`, CHECK 제약, 생성 컬럼, 인덱스 길이, DDL 잠금은 대상 MySQL에서 다시 확인한다.
- 실패 시 기존 파일을 되돌리지 않고 후속 버전으로 복구할 수 있는지 확인한다.
